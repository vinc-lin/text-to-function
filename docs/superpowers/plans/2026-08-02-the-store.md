## Where things live

`SqliteVehicle` already opens the only connection, so it keeps owning it. `sim/schema.sql` grows the new tables — it is the schema of that database. The **logic** for the new tables lives in `intake/store.py`, because intake is the I/O boundary and this is exactly its job. `Store(car.conn)` mirrors how `SqliteExecutor(car, cards)` already takes the car.

## Task 1: schema and migration

**Files:** `sim/schema.sql`, `sim/migrate.py` (new), `sim/vehicle.py`, `tests/sim/test_migrate.py` (new)

- [ ] Add to `sim/schema.sql`: `observation_raw`, `perception`, `utterance`, `turn`, `decision`, `schema_version`, and the two indices — all exactly as §3 of the spec gives them.
- [ ] `operation_log` gains `turn_id INTEGER REFERENCES turn(id)`. **This is the migration path's first real use** — an existing table with existing rows.
- [ ] `sim/migrate.py`: `migrate(conn)` reads `schema_version`, applies each step in order, writes the new version. Version 0 = a database with no `schema_version` table, i.e. every car file that exists today.
- [ ] `SqliteVehicle.init_schema()` calls `migrate()` after the `CREATE TABLE IF NOT EXISTS` pass.

**Tests:** a fresh DB lands at the current version · a version-0 DB (created from the *old* schema, checked in as a fixture or built inline) migrates without data loss and keeps its signal rows · migrating twice is a no-op · an unknown future version raises rather than guessing.

That last one matters: a store opened by an older binary must refuse rather than silently misread rows it does not understand.

- [ ] commit: `feat(sim): a schema that can change shape`

## Task 2: `intake/store.py`

**Files:** `intake/store.py` (new), `tests/intake/test_store.py` (new)

`Store(conn)` — every read and write of the new tables, and nothing else.

```python
put_raw(source, at, payload, expires_at=None) -> int      # returns raw_id
pending(now, limit=None) -> list[RawRow]                  # processed_at IS NULL, (at, id) order
mark_processed(raw_id, at, error=None) -> None
put_perception(raw_id, at, key, value, confidence, ttl, source) -> int
put_utterance(raw_id, at, text) -> int
open_turn(raw_id, at, kind) -> int
close_turn(turn_id, reply) -> None
put_decision(turn_id, subject, verdict, chosen, reason, suppressed_by) -> int
newest_perception(key) -> Optional[Row]                   # newest, NOT filtered by liveness
live_perception_keys() -> list[Row]                       # newest per key, NOT filtered
```

**The last two return the newest row without testing liveness, and that is deliberate.** Liveness is `Observation.is_live`, in Python, one definition shared by both stores. A `WHERE at + ttl >= now` here would return an older live row when the newest has expired, resurrecting a belief that today reads as gone — §5 of the spec.

**Tests:** each writer round-trips · `pending` respects `(at, id)` order and excludes processed rows · `mark_processed` with an error still marks it processed · `newest_perception` returns the newest even when expired · out-of-order inserts still yield the newest by `at`.

- [ ] commit: `feat(intake): the store — every row in and out`

## Task 3: `SceneContext` becomes a query

**Files:** `scene/context.py`, `cli/session.py`, tests throughout

The class keeps its name and its four methods (`update`, `get`, `live`, `clear`) because `WorldView` binds `get` and `live` and every rule sits above that. Only the backing changes: `SceneContext(store)` instead of an internal dict.

- [ ] `update(obs)` → `store.put_perception(...)`. `get(key, now)` → `store.newest_perception(key)`, then `Observation.is_live(now)` in Python. `live(now)` → `store.live_perception_keys()`, filtered the same way. `clear()` → deletes the perception rows for this session.
- [ ] `Session.build` constructs `Store(car.conn)` and hands it to both the engine's `SceneContext` and the `WorldView`.
- [ ] **Both proof obligations run here and must be byte-identical.** This is the task most likely to break them.

**Tests:** every existing `tests/scene/test_context.py` test must pass unchanged — that file *is* the spec for this behaviour, including the inclusive expiry boundary and the out-of-order-arrival rule. If one needs changing, the backing changed behaviour and that is a finding.

- [ ] commit: `refactor(scene): perception is a query, not a dict`

## Task 4: `ingest` writes, and `process_pending`

**Files:** `intake/ingest.py`, `tests/intake/test_ingest.py`

- [ ] `ingest(input)` writes `observation_raw` **first**, then dispatches, then writes the output rows: `open_turn` → the handler → `put_decision` per clause or rule → `close_turn(reply)`.
- [ ] `Utterance` also writes `utterance`; `Percept` also writes `perception`; `SignalWrite` writes the signal as today.
- [ ] `process_pending(now)` — §4 of the spec. Explicit, never a timer. Takes pending rows in `(at, id)` order, dispatches each, marks each processed. **An input that raises is marked processed with its error**, so it neither blocks the queue nor vanishes.
- [ ] Where do decisions come from? Voice: `RouteResult.clauses` gives clause, band, chosen. Scene: `engine.explain()` gives rule id, verdict, reason, suppressed_by. Both already exist — this task records them, it does not compute anything new.

**Tests:** a raw row appears for every input · a voice input produces a turn with the reply and one decision per clause · a scene observation produces a turn and one decision per rule · a raising input is marked processed with its error and the next pending row still runs · `process_pending` on an empty queue is a no-op · order is `(at, id)`.

- [ ] commit: `feat(intake): every input recorded, every decision written down`

## Task 5: retention and the privacy switch

**Files:** `intake/store.py`, `cli/session.py`, `cli/__main__.py`, `ui/`, tests

- [ ] `Store.sweep(now)` deletes `observation_raw` rows with `expires_at <= now`. Parsed rows survive — a run stays replayable at the belief level after the words are gone.
- [ ] `Session.build(raw_capture=True)`; `--no-raw-capture` stores the parse and never the payload.
- [ ] A default retention window on raw voice, configurable, applied at `put_raw`.

**Tests:** a swept raw row leaves its perception and utterance rows intact · `--no-raw-capture` writes no payload but the parsed rows still appear · sweeping twice is a no-op · a row with `expires_at IS NULL` is never swept.

- [ ] commit: `feat(intake): retention, and a switch for the words`

## Task 6: the completeness test

**Files:** `tests/intake/test_completeness.py` (new)

"The database is the record" is a property, not a promise. §12.4.

- [ ] Drive every path — a routed utterance, a refused command, a scene that warns, a scene that stays silent, a consent that executes, a consent declined, an input that raises — and assert each leaves the rows it should.
- [ ] Assert the **negative** too: nothing reaches the car without an `operation_log` row carrying a `turn_id`, so an execution cannot be untraceable.

## Task 7: the environment simulator

**Files:** `sim/environment.py` (new), `tests/sim/test_environment.py` (new)

Generates plausible data for all three sources **into `observation_raw` only**, letting `process_pending` do the rest — so simulated and real inputs travel exactly the same path. A generator writing parsed rows directly would be exercising a path nothing else uses.

- [ ] A `Scenario` describing what happens over a span of simulated time: the car's motion, what the cameras see, what the driver says and when.
- [ ] Deterministic given a seed, so a run is reproducible and a failure is re-runnable.
- [ ] At minimum, ship the scenarios that correspond to the existing gold rows, so the generator can be checked against something already agreed.

**Tests:** the same seed produces the same rows · every generated row is a valid `Input` (i.e. its source declares its payload type) · a generated scenario processed through `process_pending` reaches the same outcome as the hand-authored gold row it mirrors.

That last test is the one worth the most: it is the only thing connecting generated data to something a human agreed with.

- [ ] commit: `feat(sim): an environment that writes rows`

**Files:** `eval/measure_store.py` (new), and a section appended to `docs/TEST_REPORT.md`

§9 of the spec. Four numbers, measured, not estimated:

- [ ] write cost per perception frame — dict write today versus a row
- [ ] rule evaluation: N queries versus N dict reads, per rule per event
- [ ] end-to-end against the 50–85 ms baseline
- [ ] write volume at 10 Hz, extrapolated to bytes/hour

**Report them honestly, including if they are bad.** A bad number stops the work; it does not get optimised around on the way past. State the machine, and state plainly that none of it is SA8797.
